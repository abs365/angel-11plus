# ALI Parent Intelligence

**Phase:** ALI 1.4 — Parent Intelligence. Uses ALI to improve Parent Insights. Only enhances subjects that currently have ALI support (Verbal Reasoning); every other subject continues using existing logic, unchanged.

**Companion documents:** `ALI_MISSION_ENGINE.md` (Phase 1.3, the same bridge pattern this phase extends), `ALI_LEARNING_MODEL.md` §5 (the original design proposal this narrows and implements), `ALI_DECISION_LOG.md` Decision 24 (the `Math.max` ratchet this phase works around without modifying).

---

## 1. Competency summaries

`ParentReport.competencySummaries` (new field, `types/ali/parentSummary.ts`) is an array of one `CompetencyParentSummary` per subject with real ALI data — today, at most one entry, for Verbal Reasoning, and only once a student has completed at least one adaptive mock. Each entry has four buckets, in plain parent-facing language with **no technical terms** (`mastery_state`, `competency`, percentages, and question counts are never surfaced — only competency names and encouraging sentences):

| Bucket | Meaning | Derived from |
|---|---|---|
| **Strengths** | Competencies your child has mastered, excluding ones mastered *this session* | `masteredCompetencies` minus `recentlyMasteredCompetencies` |
| **Improving** | Competencies attempted, not weak, not yet mastered — genuinely "on track" | `attemptedCompetencies` minus `masteredCompetencies` minus `weakCompetencies` |
| **Focus Next** | Competencies currently flagged weak | `weakCompetencies` (same ALI-native signal Daily Missions already use, Phase ALI 1.3) |
| **Recently Mastered** | Competencies that *became* mastered as of the most recent mock | New in this phase — a diff against the previously cached signal, not a time window (§2) |

A competency never appears in two buckets simultaneously — a just-mastered competency shows in **Recently Mastered** only, not duplicated into **Strengths**, so the parent sees one clear headline per competency rather than repeated mentions.

### Where this replaces percentage-first messaging

`buildParentInsights()`'s existing "strong-subject"/"weak-subject" insights, and `buildFocusAreas()`'s weak-subject cards, now **exclude** any subject with real ALI data (`hasRealAliData()` — a signal exists and has at least one attempted competency). For Verbal Reasoning once it has data, the parent no longer sees *"Verbal Reasoning is currently below the 55% threshold"* — they see the competency summary above instead. **Every other subject's insights and focus-area cards are generated by the exact same, unmodified code path as before.**

## 2. Learning Gain (internal only)

`UserProgress.aliLearningGain` (new, additive field, `types/ali/learningGain.ts`) stores a per-subject `{ delta, cumulative, computedAt }` snapshot — a measure of improvement *over time*, not a raw score:

```
delta = (newlyMastered × 3) + (newlyAttempted × 1) + (recoveredFromWeak × 1) − (newlyWeak × 2)
```

Computed once per mock (`lib/ali/learningGain.ts`'s `computeLearningGainDelta()`), comparing the new competency signal against the previously cached one. Symmetric by design — a student who regresses (a previously-mastered competency turning weak) gets a genuinely **negative** delta, not just a smaller positive one. `cumulative` is a running total across every recorded mock, giving a real trend line.

**Not exposed anywhere in this phase.** `ParentReport` has no Learning Gain field; no UI component reads `aliLearningGain`. It exists purely as internal data for a future phase — most plausibly the "Readiness Shadow Model" flagged back in `ALI_DECISION_LOG.md` Decision 24, which needs exactly this kind of trend signal to build a readiness score that isn't gated on the `Math.max`-ratcheted single score.

## 3. Fallback behaviour

Three independent guarantees, all verified via a regression check (thrown-away validation script, same pattern as prior phases) comparing this phase's output against a reference implementation of the pre-1.4 formula:

1. **A student with no ALI data at all** — every subject falls through to the unmodified `buildParentInsights()`/`buildFocusAreas()` logic; `competencySummaries` is an empty array.
2. **An ALI signal that exists but has zero attempted competencies** (e.g. bridge-written before any question was answered — not expected in practice, but the guard is real) also falls through to the legacy formula, exactly mirroring the same fallback rule Daily Missions established in Phase ALI 1.3.
3. **A student with ALI data for Verbal Reasoning but not for any other subject** — English, Maths, Vocabulary, Writing, and the three other reasoning subjects generate insights and focus areas exactly as they did before this phase; only Verbal Reasoning's presentation changes.

## 4. Future expansion

Nothing here is Verbal-Reasoning-specific by construction, matching the same principle established in `ALI_MISSION_ENGINE.md` §4:

- `buildCompetencySummaries()` iterates `p.aliCompetencySignal` generically — any future ALI-covered subject appears automatically once it starts writing signals via the same bridge.
- `computeLearningGainDelta()`/`updateLearningGain()` take `subject` as a parameter throughout — no hardcoding.
- The one recurring cost per new subject (same as Phase 1.3): its own hand-tagged question bank, its own adaptive mock route, and an entry in the shared `COMPETENCY_LABELS` map (`lib/ali/labels.ts`) for its competency codes.

**Natural next candidates once a second ALI subject exists:** exposing Learning Gain in the UI (a trend chart, once there's enough real data to make one meaningful), and using it as an input to the Readiness Shadow Model rather than leaving it purely internal.

## Explicitly out of scope for this phase

- `Math.max` score ratcheting — untouched, per this phase's explicit safety instruction (same constraint as Phase 1.3).
- Any change to Readiness, Replay, Confidence, or Daily Missions — `ALI_LEARNING_MODEL.md`'s other proposed evolutions remain their own separate, unscheduled phases.
- Expanding ALI to any subject beyond Verbal Reasoning.
