# New Angel Visual System and Rendered Copy Quality Gate — Remediation

## Colour system root cause

`--color-primary` (globals.css) had been reassigned from purple to a deep forest green in an earlier round (AN-108), per a Founder direction current at the time ("Primary actions: deep forest green"). `Button.tsx`'s primary variant and `Card.tsx`'s `PremiumCard` (Dashboard Hero, Angel Plus Hero) were updated to match — but the much larger number of components elsewhere in the product (PathwaySwitcher, Beta, Testimonial, Mock Centre, and more) had never adopted the token and kept hardcoded purple-600/700. That divergence, not random recolouring, is what produced the "visually isolated" saturated-green surfaces the Founder flagged: two components matched an abandoned direction while the rest of the product had already settled on purple.

**Fix:** restored `--color-primary`/`--color-primary-hover` (light and dark) to purple, matching the Founder's current explicit "PRIMARY BRAND: Angel purple" direction and what most of the product already does. `Button.tsx`'s primary variant restored to purple-600/700. `PremiumCard` changed from a solid green-800 fill to a light surface (`bg-white`/`bg-gray-900`) with a soft purple border, matching the Founder's "PRIMARY SURFACES: white and restrained neutral... communicate value through hierarchy and content, not colour volume" direction — Dashboard Hero and Angel Plus Hero content recoloured to match (dark text on light surface, purple accent pills/icons, replacing white-on-green). Two remaining hardcoded `bg-green-700` primary buttons in `app/dashboard/page.tsx` (Start Today's Mission, Start Learning) fixed to purple for consistency.

Spot-checked for other large saturated surfaces across `app/learning-intelligence/**`; the only matches found were small icon-badge accents (e.g. `bg-purple-100` icon containers), already consistent with the "soft purple/lilac" contextual role — no further changes needed. Green usage elsewhere (correct-answer highlighting, "Strong" score badges, success checkmarks) is semantically appropriate per the Founder's own explicit "green must primarily communicate genuine success" allowance and was left unchanged.

## Hidden zero-width dashboard element

Investigated further this round. Next.js's own prefetching documentation (`node_modules/next/dist/docs/01-app/02-guides/prefetching.md`) confirms prefetch populates a client-side cache of RSC payload/JS bundle, not a second mounted, hidden DOM tree — ruling out the "background prefetch pre-render" hypothesis from the previous round. Re-tested extensively on a genuinely fresh browser session against stable production, including the exact conditions that had previously shown two `<main>` elements (pathway set to `csse`, full reload, repeated checks over several seconds): the duplication did not reproduce at all, across 8 repeated checks. Conclusion: most likely a transient artifact of the previous session's own rapid, repeated deploy-and-test cycle (many deployments and page loads within minutes), not a persistent code defect. Classified **RESOLVED** on this evidence; if the Founder observes it again on a specific device, the next report should capture the exact reproduction steps and device/browser so it can be chased further.
