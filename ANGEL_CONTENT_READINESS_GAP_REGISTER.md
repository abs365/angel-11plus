## Addendum — Phase 10: Zero Usage/Performance Telemetry, Root Cause (2026-09-05)

**Root cause: proven, definitive, category = "emitted but not persisted" — specifically, a real write path exists in application code and IS called from live production Practice routes on every answered question, but every one of its writes is silently blocked by a Row-Level Security gap that a later, unrelated security-hardening migration introduced without accounting for this dependency.**

**Evidence chain:**

1. **A real write path exists and is correctly designed.** `lib/ali/history.ts`'s `recordOutcome()` (lines 326-342) reads `ali_question_bank.usage_count`/`avg_success_rate`, computes an updated running average, and writes it back — best-effort, never blocking the caller, exactly the pattern this codebase uses elsewhere for non-critical side effects. This is not a stub or a placeholder; it is complete, correct code.
2. **It is genuinely wired into live production.** `recordOutcome()` has 23 real call sites across the codebase, including `app/learning-intelligence/practice/[area]/page.tsx` — the actual, live Practice session runner — which calls it with `current.id` (a real `ali_question_bank.id`) on every answered question (line 482-490 of that file). This rules out "not emitted" entirely: the write is attempted on real production traffic, repeatedly, today.
3. **The write is structurally blocked at the database layer.** Grepping every RLS policy ever created against `ali_question_bank` across all 227 migrations (`create policy ... on public.ali_question_bank`) finds exactly one policy, a `for select` policy, created/recreated four times (migrations 020, 069, 084, 100) as its predicate was refined. **No `for update` (or `for all`) policy has ever been created on this table.**
4. **This was a deliberate, disclosed security decision that did not anticipate this consequence.** Migration 084's own header is explicit: it found RLS had been disabled since migration 005, re-enabled it, and *intentionally* created only a SELECT policy — its own comment states the reasoning verbatim: *"No INSERT/UPDATE/DELETE policy is created for anon/authenticated: once RLS is enabled, the absence of such a policy means Postgres denies those operations to both roles by default — **closing the unauthorised-write path** without a separate explicit deny rule."* This was correct and necessary as a security fix (Gate 001 P1 finding #2, Decision 130 — closing a real risk where any authenticated user could otherwise mutate question content directly). It had a real, undocumented side effect: it also silently disabled the one *legitimate* write this table needed (the telemetry aggregate in `recordOutcome()`), and nothing in migration 084 or any later migration re-opens a narrow path for it.
5. **Why this fails silently rather than erroring loudly.** An `UPDATE ... WHERE id = X` against a row an RLS policy set makes invisible-for-write matches zero rows — Postgres/PostgREST does not raise a permission-denied error for this case, it simply reports zero rows affected, which is not treated as an error in `recordOutcome()`'s already-correct "best-effort" design (`bankUpdateError` stays null). The code has been silently failing exactly as its own defensive design would fail on any other soft error — it was never wrong to tolerate a missing row; it had no way to know the row was being hidden from it by policy, not absent.
6. **Alternative explanations checked and ruled out**: no privacy-intentional decision was found anywhere in `ALI_DECISION_LOG.md` naming `usage_count`/`avg_success_rate` specifically (searched); this is aggregate, non-learner-identifying, question-level data, not a privacy-sensitive field by nature. An anon-key read-visibility artifact was also ruled out: the SELECT policy that exists is a genuine allow-list on row visibility (`eligibility_status`-based), not a column-level mask — `usage_count`/`avg_success_rate` are returned by the same query as every other visible column, so a live anon read genuinely reflects the true stored value (0/null), not a masked one.

**No code fix was made by this fork.** Per this Phase's own instruction ("fix only when root cause is proven and the correction is privacy-safe") and this repository's own established migration governance (every schema/RLS change is drafted for Founder review, never applied directly by this environment, which holds no production write credentials in any case), the correct minimal fix was specified here for the Founder/next increment to apply, **not created as a migration file by this fork** — a Question Factory family-model migration was in flight concurrently in this same working tree, and picking a migration number risked a real file collision.

**UPDATE (same day, after the family-model migration claimed number 228)**: the exact fix specified below has now been written as `supabase/migrations/229_question_bank_telemetry_write_path_restoration.sql` (NOT APPLIED, structurally tested — `tests/supabase/questionBankTelemetryWritePathRestoration.test.ts`, 9/9 passing). It is byte-for-byte the same GRANT + policy shape this addendum already specified, sequenced correctly after migration 228. This closes the "specified but not written" gap; applying it remains a Founder action, per this repository's own standing migration-application convention.

**Recommended fix (privacy-safe: touches only two non-identifying, aggregate, question-level columns; does not reopen migration 084's actual security concern, which was arbitrary content mutation)**:

```sql
-- Grant column-scoped UPDATE only -- authenticated users still cannot
-- modify prompt/answer/eligibility_status/etc., only these two
-- non-sensitive rolling-average telemetry columns.
grant update (usage_count, avg_success_rate) on public.ali_question_bank to authenticated;

create policy ali_question_bank_telemetry_update on public.ali_question_bank
  for update to authenticated
  using (eligibility_status is distinct from 'mock_eligible' or public.is_current_user_admin())
  with check (eligibility_status is distinct from 'mock_eligible' or public.is_current_user_admin());
```

The `USING`/`WITH CHECK` predicate deliberately mirrors the existing SELECT policy's own eligibility-status gate exactly, so a learner can only bump telemetry on rows they could already see — never on sealed/Mock-reserved content, preserving the Practice/Mock firewall's own boundary for this new write path too. Once applied, `usage_count`/`avg_success_rate` should begin incrementing on the very next Practice-session answer submitted after the migration is live, and this can be verified with the same read-only anon-key query already used to discover the defect (a rising `usage_count` on any previously-zero row is direct, immediate confirmation).
